# Методология профилирования

## Инструменты (запускает `.github/workflows/profile.yml`)

1. **criterion** (`bench.yml`) — время, статистика, история на gh-pages,
   алерт при регрессе >150%.
2. **perf + FlameGraph** (job `perf`) — выборка стека 299 Гц с DWARF,
   развёртка в SVG flamegraph.
3. **callgrind** (job `callgrind`) — детерминированные счётчики инструкций
   (Ir), не зависит от PMU, идеален для сравнения «до/после» по сложности.

## Как читать отчёты

- `perf-report.txt`: колонка `Overhead` — доля CPU; флаг `--no-children`
  означает собственное время функции (без вызываемых).
- `flamegraph-*.svg`: ширина блока = доля CPU; ищи широкие плоские «полки» —
  это кандидаты на переписывание.
- `callgrind-report.txt`: колонка `Ir` (instruction count) — точная
  относительная метрика алгоритмической стоимости.

## Правила выбора цели

- Кандидат: функция с >= 5% CPU в горячем примере.
- После оптимизации: сравнить callgrind Ir и criterion-время до/после.
- Регресс criterion в CI — откат коммита.

## Локально

```bash
cargo bench --workspace
cargo build --release --example hotspot -p foxjson
perf record -e cpu-clock -g -- target/release/examples/hotspot
perf report
```

Переменные workload'а: `FOX_HOTSPOT_TABS`, `FOX_HOTSPOT_PARAS`,
`FOX_HOTSPOT_ITERS` (см. `examples/hotspot.rs` каждого крейта).

## Локально без perf/valgrind: SIGPROF-сэмплер (итерация 5)

В контейнерах без root (`perf` требует доступ к счётчикам ядра,
`valgrind` не установлен) работает собственный выборочный профайлер:
`tools/sampler.rs` — ITIMER_PROF шлёт SIGPROF каждые ~250 мкс CPU-времени,
async-signal-safe хендлер пишет RIP в lock-free ring buffer, адреса
символизируются `tools/symbolize.py` через `nm`.

```bash
# сборка: не-PIE обязателен (иначе RIP != файловым адресам);
# cargo rustc применяет флаги только к финальному примеру, не к proc-macro
cargo rustc --release --example prof_json -p foxjson -- \
    -C relocation-model=static -C link-arg=-no-pie
FOX_PROF_ITERS=2000 ./target/release/examples/prof_json
python3 tools/symbolize.py target/release/examples/prof_json /tmp/foxjson.prof --top 20
```

Для foxsearch — `prof_search` (env: `FOX_PROF_PARAS`, `FOX_PROF_ITERS`).

Ограничения: адреса в libc (memcpy/malloc) без карт процесса уходят в
последний символ (`_fini`) — большой `_fini` означает libc-накладные
расходы (для точности: читать `/proc/self/maps` в момент остановки).
A/B ядер скана на шумных виртуалках — `examples/scan_ab.rs` в foxsearch:
старое/новое ядра в одном процессе, попеременные раунды, медианы.

## Стабилизация бенчей против layout-лото (итерация 18)

Уроки сессий 11-13: на этой VM сдвиг кода на +29 байт менял
`parse/foxurl/corpus-all` на +-18% при неизменных абсолютных временах
отдельных URL — структурные выигрыши 5-10% были неотделимы от шума.
Причина: вход функции попадает на неудачную границу fetch-окна / DSB-сета
в зависимости от размеров ПРЕДЫДУЩИХ функций; любое изменение кода
перебрасывает кости для всего, что идёт после.

Мера (сессия 14): три нейтральных pad-возмущения крейта foxurl (pad-функция
0/~40/~500Б, вызывается бенчем вне измеряемого цикла), замер corpus-all
на каждом состоянии:

| конфиг | P0 | P1 | P2 | разброс |
|---|---|---|---|---|
| без флагов | 844.8 ns | 877.3 ns | 862.7 ns | **+3.84%**, все точки различимы |
| CGU=1 + align64 | 783.4 ns | 789.1 ns | 799.5 ns | **+2.06%**, P0/P1 неразличимы |

Принято в `.cargo/config.toml` (действует на bench, test и CI Benchmark):

```toml
[build]
rustflags = ["-C", "codegen-units=1", "-C", "llvm-args=-align-all-functions=6"]
```

- `codegen-units=1` — один CGU на крейт: детерминичный кодgen, убирает
  лотерею CGU-партиционирования (и попутно -7% абсолюта на corpus-all);
- `-align-all-functions=6` — каждый вход функции на границе 64Б:
  выравнивание горячих входов перестаёт зависеть от соседей.

Остаточные ~2% — neighborhood-эффекты (соседний код в I-cache/DSB),
полно не убираются; порог достоверности структурных изменений на этой VM
снижен с ±10-15% до ±3-5%.

ВАЖНО: env `RUSTFLAGS` (если задан) полностью перекрывает config-флаги —
не-PIE проф-сборки (секция выше) работают как раньше. Смена конфига
сдвинула ВСЕ абсолютные числа бенчей один раз (см. WORKLOG, сессия 14);
отношения same-run (foxurl vs url, foxjson vs serde_json) сопоставимы.

## Предоценка плотности хитов ДО реализации (итерация 24)

Правило «эффект >> 15% ДО реализации» исполняется инструментом
`tools/hit_density.py`: точная реплика RARITY/pick_filter_byte/sample::url_stream
и фикстур бенчей (все детерминированы) считает НАСТОЯЩИЕ плотности хитов
сканера MultiNeedle без запуска бенчей:

- classifier — состав множества S, размер/наполнение групп, плотность хитов,
  симуляция LUT-выживания (доля ложных хитов, убитых на каждом уровне, доля
  реальных совпадений), верхняя граница выгоды парного скана (X, b);
- multi-N — плотность объединения фильтр-байтов -> P(m != 0) на 32Б-блок ->
  верхняя граница выгоды inner-collect.

Метод (урок сессии 20): долю зоны профиля надо делить на (фильтруемое) и
(структурное) ДО экспериментов — «48.6% verify_at» может означать «0%
сжимаемо», если выжившие хиты — реальные совпадения, а ложные уже убиты
LUT до нуля. Фикстуры в python-реплике дублируются НАРОЧНО (инструмент не
зависит от cargo) — при изменении RARITY/стримов синхронизировать вручную.

### Отношения fox/эталон как слой вердикта (итерация 32): калибровка, асимметрия знака, маскировка

Гипотеза «для FAST первичный сигнал — fox/std отношения» проверена на
всех 14 одноклассных парах 10 прогонов (код крейтов идентичен с
итерации 26 — любая пара чистый эксперимент). Отношение считалось
только с fox-стороны, агрегат — МЕДИАНА дельт по крейту (foxjson 4,
foxurl 17, foxsearch 3 отношения; медиана глушит выбросы отдельных
микробенчей).

**Калибровка (8 тихих пар, 24 крейт-медианы):** шум медиан max +4.3%
(foxjson) / +0.8% (foxurl) / +0.3% (foxsearch), минимум -1.5%, span
крейт-медиан <= 4.8 п.п.

**Скоростной дрейф отношение ИММУНИЗИРУЕТ:** пара FAST 470d380/9337c7e —
canary +14.4%, все крейт-медианы в пределах +-1% (foxjson -0.7, foxsearch
-0.1, foxurl +0.8). Гипотеза подтверждена для равномерного дрейфа:
fox и эталон масштабируются одинаково, отношение стоит на месте.

**Микроархитектурный дрейф отношение НЕ иммунизирует** — крейт-медианы
движутся в ОБЕ стороны: 6 дрейф-пар дают span 40-73 п.п., минимум
-6.4..-29.2% (что-то относительно УСКОРЯЕТСЯ), максимум +10.9..+46.6%.

**Асимметрия знака — главный дискриминатор:** регресс гонит отношения
своего крейта только ВВЕРХ (код не делает fox относительно эталона
быстрее); дрейф обязан показать хотя бы один крейт с отрицательной
медианой. На 14 реальных парах + 3 синтетических разделение полное:
тихие max +4.3 / мин -1.5 против дрейфа мин <= -6.4.

Пороги в tools/bench_history.py: ELEVATED +8% (медиана крейта >= —
подозрение на регресс крейта), SUPPRESSED -5% (относительное ускорение —
только среда). Запас против шума тихих пар ~1.6-2x.

**Апгрейд --check:** (1) вердикт всегда печатает крейт-медианы отношений;
(2) широкий разброс + крейт <= -5% => ДРЕЙФ с указанием двустороннего
движения; (3) широкий разброс + top-крейт >= +8% при отсутствии
подавленных => РЕГРЕСС, ЗАМАСКИРОВАННЫЙ РАЗБРОСОМ (новый путь exit 1:
локализованный регресс >= 10% бенчей растягивает p90 и раньше выглядил
как ДРЕЙФ); (4) узкий РЕГРЕСС: отношения подтверждают крейт либо
подсказывают равномерный дрейф скорости (все бенчи во флагах, отношения
тихие).

Тесты: tools/test_bench_history.py в репо (13/13, детерминированная
синтетика 81 бенч — окна p10/p90 как в продакшене). Живая валидация:
a8ab2dc/b4e4b57 ДРЕЙФ exit 3 c диагностированным двусторонним движением
(foxjson -18.1, foxurl -25.1); реплеи 9337c7e/470d380 ПАРИТЕТ и
2052ec8/573f613 ДРЕЙФ воспроизведены с расширенной диагностикой.

**Ограничение (честно):** регресс ПОД микроархитектурным дрейфом одним
сравнением не разрешается — синтетика +25% foxjson на дрейф-паре
a8ab2dc/b4e4b57 поднимает медиану крейта лишь с -18.1 до +2.4 (тихо!),
пока foxsearch +46 / foxurl -25 доминируют картину. Такой парой вердикт
ДРЕЙФ -> повторный прогон остаётся единственным разрешающим механизмом.
Цена ошибки асимметрична и сознательно смещена: ложный РЕГРЕСС стоит
повторного прогона, ложный ПАРИТЕТ — пропуска регресса.

Нюанс метода: в probe-скрипте итерации ключ отношения склеивался по
последним сегментам — parse/foxurl/corpus-all и canonical/foxurl/corpus-all
давили друг друга (медиана -26.4); в tools-реализации ключей нет,
медиана по всем 17 отношениям foxurl = -25.1 — эталонная.

### Пересмотр порога на 21 паре и решение о FAST-субклассификации (итерация 33)

Условие ">=10 одноклассных пар" достигнуто: 12 прогонов (CLASSIC x6,
MEDIUM x3, FAST x3) => 21 пара идентичного кода. 6-й живой вердикт:
4a3c7e3 [CLASSIC] vs 2052ec8 [CLASSIC] ПАРИТЕТ — самый чистый в истории
(median +0.00%, разброс 2.6 п.п., canary +0.16%, отношения <= +-1.6%):
в пуле есть VM одной микроархитектуры, дающие воспроизводимость ~1%.

**Пересмотр порога (решение: оставить +20% как триаж):**
- дрейф-пар 7 из 21 (все 5 пар 573f613 — одиночная VM 1261716 против
  кластера 1355-1360K — плюс 2 MEDIUM-пары a8ab2dc); слой отношений
  корректно развёл все 7 в ДРЕЙФ, ложных РЕГРЕСС нет;
- флаги >20% на ТИХИХ парах: 1 на ~1050 сравнений (0.1%) —
  serialize/foxurl/6 +20.9% на FAST-паре 3007eaa/470d380;
- микробенчи (<200 нс) — единственный класс у порога: тихий max 7.1%
  (CLASSIC) / 9.9% (MEDIUM) / 20.9% (FAST). На FAST-парах таймерная
  гранулярность 14 нс на 67-нс бенче даёт шум, неотличимый от порога.
  ЗАФИКСИРОВАНО: единичный флаг микробенча при тихом крейт-медиане
  отношений — неразрешим одним сравнением (медиана из 17 отношений
  нечувствительна к одному бенчу); ответ — повторный прогон, код
  крейтов при этом не трогать до подтверждения вторым прогоном;
- абсолютный пол для микробенчей по-прежнему не нужен (дрейф-осознанный
  вердикт + слой отношений закрывают вопрос дешевле отдельного правила).

**FAST-субклассификация (решение: НЕ вводить):**
- крейт-медианы отношений на всех 3 FAST-парах в пределах +-1.7% —
  слой отношений полностью нейтрализует скоростной разброс canary
  (712K..815K, 14.4%);
- квартили canary при 3 прогонах дали бы 1-2 прогона на подкласс => пар
  нет, exit 2 на недели — цена без пользы;
- дрейф-пар в FAST: 0 из 3 (гетерогенность пула пока не задевала FAST);
- условия возврата к вопросу: (а) >=8 FAST-прогонов; (б) FAST-пара,
  где слой отношений даст неоднозначный сигнал (top >= +8% без
  подавленных); (в) постмортем пропущенного регресса.
- остаточный риск НЕ специфичен для FAST: одиночный микробенч-регресс
  невидим крейт-медианам в любом классе; покрытие — узкий разброс +
  абс. флаг (уже работает:serialize/foxurl/6-кейс был пойман флагом).

## Переоценка fused-auth-scan v0.8.1 на серверном CPU (итерация 34)

Ветка experiment/fused-auth-scan (foxurl v0.8.1: однослитный скан авторити
через AUTH_SCAN_* бит-таблицы, второй проход scan_host_domain убран) была
помечена в сессии 29 «archived for server-CPU re-evaluation». Переоценка
выполнена парным прогоном нового workflow bench-exp.yml (workflow_dispatch:
job экспериментального ref + парный контроль main; artifact-only — gh-pages
НЕ пишется, история пула не загрязняется; run 40160875884).

**Констатация о базе сравнения:** ветка форкнута от a85e916 (v0.7.1);
foxurl на main с тех пор не менялся — foxurl-сравнение валидно. foxsearch
на ветке старый (без итераций 22-26), поэтому classifier/multi bench'и на
ветке отсутствуют вовсе (exp-прогон: 60 bench-строк, main: 75), а
foxsearch-контроль ограничен однопрочными find/* (не менялись между
поколениями; abs +0.3..+1.6%).

**Числа (CLASSIC vs CLASSIC, canary 1362677 vs 1358203, разнос 0.33%):**
- per-URL parse/foxurl/0..13: 13/14 улучшены, abs-медиана -10.9%
  (диапазон -4.1..-18.0%); единственный минус — parse/7 +20.8%;
- canonical-агрегаты: corpus-all -4.7%, dirty-all -5.9% — улучшены;
- АГРЕГАТ parse/foxurl/corpus-all: +13.9% abs (+8.3% по отношению) — РЕГРЕСС;
- serialize/dirty-all +4.9%; serialize/foxurl/6 +20.2% (известный 14нс-флаппер).

**Вердикт: ОСТАЁТСЯ В АРХИВЕ.** Рамка решения зафиксирована до просмотра
foxurl-данных: (1) per-URL медиана <= -5% — ДА (-13.4% по отношениям);
(2) парность runner'ов, max |abs| идентичного кода <= 3% — ДА (2.02%);

-4.1..-18.0% abs), но агрегат corpus-all проигрывает на обеих (Bench-VM:
flat -0.4%; сервер: +13.9%) — лотерея раскладки на уровне набора URL
подтверждена независимо на двух машинах. Слияние сломало бы первичный
мониторинг --check (cargo-медиана foxurl ушла бы к нулю при +14% на
флаговом bench'е). Повторная оценка имеет смысл только вместе с
IPv6-canon/foxjson-strings/AVX-512 и лишь при появлении способа удержать
агрегат (например, выравнивание горячего цикла или #[cold] на редком пути).

### Межпрогонный шум партнёрских (std) бенчей — новое знание о пуле

Парный прогон вскрыл явление: serde_json / url_crate / std-игольчатые
бенчи гуляют между ОДНОКЛАССНЫМИ прогонами с парным canary (разнос 0.33%)
и идентичным fox-кодом ДО +28%, причём СИСТЕМНО в одну сторону
(find/std/search?q +28.3%, parse/serde_json/small +19.7%, parse/serde_json/session-500
+11.7%, parse/url_crate/* +3..+11% — exp-прогон медленнее пулевых значений),
тогда как fox-бенчи того же прогона воспроизводятся в ±2% и сидят точно
на пуле. Версии зависимостей идентичны (Cargo.lock разнится только
версиями собственных крейтов), оба прогона собрались из одного поколения
rust-cache (32s/40s). Механизм НЕ установлен — кандидат: host-уровень
 среды исполнения (подсистема памяти/аллокатор/NUMA), не кодоген.
Следствия (закреплены в --check итерации 34):
- парные межхостовые сравнения: контроль идентичности кода — abs-дельты
  fox-бенчей идентичного кода, НЕ дельты индивидуальных отношений
  (партнёрский шум входит в отношения целиком, до ~28 п.п.);
- устойчивы только крейт-медианы отношений — дизайн слоя вердикта
  (итерация 32) подтверждён с новой стороны;
- часть исторических "микроарх. дрейф-пар" может включать эту
  партнёрную составляющую — при разборе дрейфа смотреть обе стороны
  пары (fox И эталон), а не только fox.

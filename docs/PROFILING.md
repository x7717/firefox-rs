# Методология профилирования

## Инструменты (запускает `.github/workflows/profile.yml`)

1. **criterion** (`bench.yml`) — время, статистика, история на gh-pages,
   алерт при регрессе >150%.
2. **perf + FlameGraph** (job `perf`) — выборка стека 299 Гц с DWARF,
   развёртка в SVG flamegraph.
3. **callgrind** (job `callgrind`) — детерминированные счётчики инструкций
   (Ir), не зависит от PMU, идеален для сравнения «до/после» по сложности.

## Как читать отчёты

- `perf-report.txt`: колонка `Overhead` — доля CPU; флаг `--no-children`
  означает собственное время функции (без вызываемых).
- `flamegraph-*.svg`: ширина блока = доля CPU; ищи широкие плоские «полки» —
  это кандидаты на переписывание.
- `callgrind-report.txt`: колонка `Ir` (instruction count) — точная
  относительная метрика алгоритмической стоимости.

## Правила выбора цели

- Кандидат: функция с >= 5% CPU в горячем примере.
- После оптимизации: сравнить callgrind Ir и criterion-время до/после.
- Регресс criterion в CI — откат коммита.

## Локально

```bash
cargo bench --workspace
cargo build --release --example hotspot -p foxjson
perf record -e cpu-clock -g -- target/release/examples/hotspot
perf report
```

Переменные workload'а: `FOX_HOTSPOT_TABS`, `FOX_HOTSPOT_PARAS`,
`FOX_HOTSPOT_ITERS` (см. `examples/hotspot.rs` каждого крейта).

## Локально без perf/valgrind: SIGPROF-сэмплер (итерация 5)

В контейнерах без root (`perf` требует доступ к счётчикам ядра,
`valgrind` не установлен) работает собственный выборочный профайлер:
`tools/sampler.rs` — ITIMER_PROF шлёт SIGPROF каждые ~250 мкс CPU-времени,
async-signal-safe хендлер пишет RIP в lock-free ring buffer, адреса
символизируются `tools/symbolize.py` через `nm`.

```bash
# сборка: не-PIE обязателен (иначе RIP != файловым адресам);
# cargo rustc применяет флаги только к финальному примеру, не к proc-macro
cargo rustc --release --example prof_json -p foxjson -- \
    -C relocation-model=static -C link-arg=-no-pie
FOX_PROF_ITERS=2000 ./target/release/examples/prof_json
python3 tools/symbolize.py target/release/examples/prof_json /tmp/foxjson.prof --top 20
```

Для foxsearch — `prof_search` (env: `FOX_PROF_PARAS`, `FOX_PROF_ITERS`).

Ограничения: адреса в libc (memcpy/malloc) без карт процесса уходят в
последний символ (`_fini`) — большой `_fini` означает libc-накладные
расходы (для точности: читать `/proc/self/maps` в момент остановки).
A/B ядер скана на шумных виртуалках — `examples/scan_ab.rs` в foxsearch:
старое/новое ядра в одном процессе, попеременные раунды, медианы.

## Стабилизация бенчей против layout-лото (итерация 18)

Уроки сессий 11-13: на этой VM сдвиг кода на +29 байт менял
`parse/foxurl/corpus-all` на +-18% при неизменных абсолютных временах
отдельных URL — структурные выигрыши 5-10% были неотделимы от шума.
Причина: вход функции попадает на неудачную границу fetch-окна / DSB-сета
в зависимости от размеров ПРЕДЫДУЩИХ функций; любое изменение кода
перебрасывает кости для всего, что идёт после.

Мера (сессия 14): три нейтральных pad-возмущения крейта foxurl (pad-функция
0/~40/~500Б, вызывается бенчем вне измеряемого цикла), замер corpus-all
на каждом состоянии:

| конфиг | P0 | P1 | P2 | разброс |
|---|---|---|---|---|
| без флагов | 844.8 ns | 877.3 ns | 862.7 ns | **+3.84%**, все точки различимы |
| CGU=1 + align64 | 783.4 ns | 789.1 ns | 799.5 ns | **+2.06%**, P0/P1 неразличимы |

Принято в `.cargo/config.toml` (действует на bench, test и CI Benchmark):

```toml
[build]
rustflags = ["-C", "codegen-units=1", "-C", "llvm-args=-align-all-functions=6"]
```

- `codegen-units=1` — один CGU на крейт: детерминичный кодgen, убирает
  лотерею CGU-партиционирования (и попутно -7% абсолюта на corpus-all);
- `-align-all-functions=6` — каждый вход функции на границе 64Б:
  выравнивание горячих входов перестаёт зависеть от соседей.

Остаточные ~2% — neighborhood-эффекты (соседний код в I-cache/DSB),
полно не убираются; порог достоверности структурных изменений на этой VM
снижен с ±10-15% до ±3-5%.

ВАЖНО: env `RUSTFLAGS` (если задан) полностью перекрывает config-флаги —
не-PIE проф-сборки (секция выше) работают как раньше. Смена конфига
сдвинула ВСЕ абсолютные числа бенчей один раз (см. WORKLOG, сессия 14);
отношения same-run (foxurl vs url, foxjson vs serde_json) сопоставимы.

## Предоценка плотности хитов ДО реализации (итерация 24)

Правило «эффект >> 15% ДО реализации» исполняется инструментом
`tools/hit_density.py`: точная реплика RARITY/pick_filter_byte/sample::url_stream
и фикстур бенчей (все детерминированы) считает НАСТОЯЩИЕ плотности хитов
сканера MultiNeedle без запуска бенчей:

- classifier — состав множества S, размер/наполнение групп, плотность хитов,
  симуляция LUT-выживания (доля ложных хитов, убитых на каждом уровне, доля
  реальных совпадений), верхняя граница выгоды парного скана (X, b);
- multi-N — плотность объединения фильтр-байтов -> P(m != 0) на 32Б-блок ->
  верхняя граница выгоды inner-collect.

Метод (урок сессии 20): долю зоны профиля надо делить на (фильтруемое) и
(структурное) ДО экспериментов — «48.6% verify_at» может означать «0%
сжимаемо», если выжившие хиты — реальные совпадения, а ложные уже убиты
LUT до нуля. Фикстуры в python-реплике дублируются НАРОЧНО (инструмент не
зависит от cargo) — при изменении RARITY/стримов синхронизировать вручную.

## Свежие SIGPROF-бейзлайны под config B (итерация 26, 2026-10-25)

Съём после отката батч-пути (36db40c): сборка prof_* с флагами не-PIE
через `cargo rustc ... --` (добавки к флагам, config B из .cargo/config.toml
НЕ перекрыт — в отличие от env RUSTFLAGS).

Команды:
```bash

    -C relocation-model=static -C link-arg=-no-pie

    target/release/examples/prof_json
python3 tools/symbolize.py target/release/examples/prof_json /tmp/foxjson_session.prof --top 18
```

Результаты (сэмплов: session 3484, nums 1859, strs 1085, foxurl 648):

| workload | лидеры (own-time) |
|---|---|
| foxjson session-5000 | parse_value_tok 46.2%, parse_string 30.7%, parse_string_slow 13.3%, first_stop_avx2 6.5%, _fini(libc) 2.9% |
| foxjson nums-5000 | parse_value_tok 77.2% (чистые числа), parse_string 22.8% (ключи) |
| foxjson strs-5000 | parse_value_tok 34.2%, parse_string_slow 29.6%, parse_string 23.3%, first_stop_avx2 9.3% |
| foxurl corpus-20000 | parse_authority_and_path 31.5%, parse_raw 16.7%, as_str 12.2%, main(харнесс) 10.3%, _fini(libc) 7.3%, parse_query 6.2% |

Выводы (предоценка, правило >>15%):

- лидеры совпадают с ЗАКРЫТЫМИ зонами (foxjson строки/числа, foxurl
  authority/IPv6, canonical-сериализация) — изменения профиля нет, зоны
  остаются закрытыми;
- parse_raw 16.67% — внутри исторического коридора 13.6-15.6% (648 сэмплов,
  CI95 ±3%): НЕ изменение профиля; содержимое уже табличный однопроходник
  (v0.6 SCHEME_TBL, v0.7 dirty-restart) — нового рычага нет;
- as_str 12.2% — цена ленивой канонизации (= canonical-бенч, история -51%),
  не новый рычаг;
- _fini (libc malloc/memcpy) 2.9-7.3% — микрозона, аллокатор не трогаем
  (zero-dep политика крейтов);
- first_stop_avx2 6.5-9.3% — микрозона (<15%), не трогать.

Итог итерации 26: новых зон >>15% вне закрытого списка НЕТ. Профили
зафиксированы как бейзлайн для следующих сессий.

## Классы CI-раннеров (итерация 27) — калибровка абсолютов

5 прогонов Benchmark на ИДЕНТИЧНОМ коде (36db40c..9b89cc1 — только
docs/CI-правки) выявили ТРИ класса скорости раннеров; межраннерный
разброс каждого бенча 49-76%, внутри-прогонный (идентичные нагрузки
find/foxsearch) 0.10-1.50%:

| класс | commit(и) | session-5000 | corpus-all | find Mozilla | multi-2 | classifier-8 |
|---|---|---|---|---|---|---|
| FAST | aa04edc, 692786f-push | 720-774K | 573-603 | 112-117K | 151-160K | 4.2-4.6K |
| MEDIUM | 36db40c, 9b89cc1 | 1063-1070K | 987-996 | 179K | 194-196K | 7.1-7.3K |
| CLASSIC | 692786f-dispatch | 1357K | 1195 | 207K | 247K | 8.4K |

(ns; канарейка классификации — parse/foxjson/session-5000: <900K FAST,
<1.2M MEDIUM, иначе CLASSIC; шаг "Runner class canary" в bench.yml
печатает класс в каждый лог и Step Summary — проверен на всех 5 логах.)

Следствия для протокола измерений:

1. Сравнивать ТОЛЬКО прогоны одного класса; абсолюты между классами
   несопоставимы (fast->classic = +85% на ровном месте);
2. Первичный сигнал регресса — внутри-прогонные отношения fox/std и
   паритет идентичных нагрузок (разброс < 1-1.5%); критерий-бейзлайны
   (save-baseline/baseline) локально — второй;
3. Алерт github-action-benchmark 150% класс-слеп: реальный регресс +20%
   невидим на его фоне, а переворот класса не должен триггерить. Алерт —
   только страховка от катастрофы, не инструмент измерения;
4. Классы отражают пул Azure (VM flavor неизвестен) — при исчезновении
   класса (обновлении пула) таблицу перевалидировать новым набором
   прогонов идентичного кода.

### Инструмент класс-осознанного вердикта (итерация 28)

`tools/bench_history.py` — анализатор `dev/bench/data.js` из gh-pages
(только stdlib). Закрывает главный пробел протокола: алерт g-a-b 150%
класс-слеп, а этот инструмент сравнивает последний прогон с последним
ОДНОКЛАССНЫМ предшественником:

- `python3 tools/bench_history.py data.js` — обзор: таблица прогонов с
  самоклассификацией по canary, тренд ключевых бенчей, внутри-прогонный
  паритет fox/эталон (27 пар: foxjson/serde_json, foxurl/url_crate,
  foxsearch/std);
- `--check [PCT]` (по умолчанию 20) — вердикт регресса; exit 0 паритет /
  1 регресс / 2 нет одноклассного предшественника (накапливать историю);
- `--fetch` — взять data.js из origin/gh-pages через git show.

Офлайн-проверено на реальных данных (3 прогона — по одному каждого
класса: 692786f CLASSIC 1357K / 9b89cc1 MEDIUM 1070K / 470d380 FAST
712K) и на синтетике (детекция +25% exit 1; паритет exit 0).

Верификация целостности истории на 470d380: 75/75 значений data.js
совпали с сырым (разбитым criterion) логом job'а после склейки пар
"ERROR-строка + bench-строка" — цепочка Split->Normalize->g-a-b->gh-pages
байт-точна.

Наблюдение по паритету между классами: ключевые отношения стабильны
(session/nums/strs 0.16-0.21x, find 0.22-0.26x на всех трёх классах);
микробенчи (<100 ns: parse/foxurl/0..13) шумят по отношению до ±20%
относительных — для них паритет смотреть по corpus-all.
